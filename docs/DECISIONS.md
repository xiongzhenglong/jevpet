# 决策记录

这里记录已经作出的关键选择及原因。新决策按顺序追加，不删除历史；被替代时标记为 Superseded。

## D-001：使用 Flutter 作为应用壳

- 状态：Accepted
- 日期：2026-09-22

选择 Flutter，以一套代码覆盖 Windows 开发预览、Android、Web，并为未来 iOS 保留路径。UI 面板、设置、调试工具和系统能力由 Flutter 承担。

## D-002：使用 Flame 承载 2D 房间

- 状态：Accepted
- 日期：2026-09-22

房间内需要游戏循环、精灵层级、坐标移动、碰撞/点击区域和时间驱动动画。Flame 负责场景层，普通应用界面仍使用 Flutter Widget。

## D-003：动画资产先做对比原型

- 状态：Pending
- 日期：2026-09-22

候选方案是序列帧 atlas 与 Rive。M1 各做一个最小样例，从美术生产成本、运行性能、状态混合和包体积决定主方案。Domain 与 Executor 不依赖具体动画技术。

## D-004：Jev 只规划受限动作

- 状态：Accepted
- 日期：2026-09-22

Jev 从版本化 Action Registry 中选择和组合能力，不生成或执行任意代码。所有计划都要经过客户端校验并拥有本地 fallback。

## D-005：高频行为本地优先

- 状态：Accepted
- 日期：2026-09-22

点击、注视、基础走动等高频交互由本地规则决定。只有多义输入和复杂组合才请求 Jev，避免延迟和成本破坏生命感。

## D-006：动态 UI 使用组件目录与 DSL

- 状态：Accepted
- 日期：2026-09-22

动态页面由预先实现的组件和受限数据协议组成。Planner 可以决定展示什么和如何组合，但不生成 Flutter 代码或任意样式。

## D-007：密钥放在服务端

- 状态：Accepted
- 日期：2026-09-22

移动端二进制无法可靠保护第三方 API Key。Jev 和对话模型请求通过自有轻量服务转发；客户端只持有面向本产品的短期凭证。

## D-008：先完成单体仓库

- 状态：Accepted
- 日期：2026-09-22

早期将 `app`、`services`、文档和资产约定放在同一仓库，降低跨电脑和跨仓库协调成本。规模或团队边界明确后再拆分。

## D-009：采用 room-first 的温暖自然视觉方向

- 状态：Accepted
- 日期：2026-09-22

首张概念图确认了移动端纵向、温暖房间、自然材质、低饱和绿色与叶耳宠物的整体方向。房间是主舞台，宠物处在可活动空间中，对话框不是页面主体。

概念图只确定氛围与信息层级，不代表逐像素实现。最终渲染风格、角色三视图、动画资产格式和常驻控件密度仍需原型验证。
