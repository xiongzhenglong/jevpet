# 项目探索摘要

这份文档沉淀项目正式启动前的讨论和代码研究。它记录“为什么最后选择虚拟宠物”，避免换电脑、换 Codex 任务或隔一段时间后，只剩下结论而忘记推理过程。

文档中的内容分为三类：

- **已确定**：可以直接指导实现，若修改需要同步更新 `DECISIONS.md`。
- **方向性判断**：值得原型验证，但不是硬需求。
- **想法池**：保留灵感，不进入当前里程碑。

## 我们对 Jev 的理解

Jev 不是以生成长文本为核心的聊天模型。它更像软件里的类型化决策层：给它当前状态和有限问题，让它返回 Choice、Score、Boolean 等可校验结果以及置信度。

一句更工程化的描述：

> Jev 是一个能理解自然语言和复杂上下文的“智能 switch”，应用负责定义允许选择的分支。

它适合分类、路由、排序、匹配、验证和从有限能力中选择下一步，不适合独自承担长文生成、像素渲染、数据库事务或任意代码执行。

## 三个参考项目带来的启发

### `jev-ultrafast`

参考仓库：[browser-use/jev-ultrafast](https://github.com/browser-use/jev-ultrafast)

它把每次浏览器观察转成动态编号的元素表，只把当前可用的操作和兼容目标交给 Jev。一次决策同时选择操作与目标；只有需要输入文本时，才让小型生成模型写文字。

最值得带进 JevPet 的原则：

- 能力空间可以随当前状态动态变化，而不必永远暴露全部动作。
- 决策结果必须落到真实、已观察、已注册的目标上。
- 模型输出不应变成选择器、坐标、脚本或任意可执行代码。
- 执行前重新验证目标，执行后独立验证结果。
- 生成式模型只补充真正需要生成的部分，不负责整个循环。

映射到宠物后，“DOM 元素表”就是此刻可见物品、逻辑位置、动画能力与状态变化范围；“浏览器操作”就是走、看、叫、吃、玩、睡等已注册动作。

### `jev-chat-jarvis`

参考仓库：[jev-chat/jev-chat-jarvis](https://github.com/jev-chat/jev-chat-jarvis)

它将任务拆成三层：Jev 判断意图、风险与最佳动作；生成模型起草候选文字；Jev 再排序，最终发送仍由用户决定。不同聊天 App 只更换采集适配器，判断和展示内核保持一致。

对 JevPet 的启发：

- “判断”和“表达”应该分开。
- Jev 决定宠物想做什么；便宜的语言模型最多决定它怎么说。
- 应用拥有最终执行权，危险或越界动作不能因为模型建议而发生。
- 输入来源可以更换：点击、文字、语音、时间事件最终都变成统一事件。
- 先做稳定内核，再给不同平台或宠物外观增加适配层。

### `awesome-jev`

参考仓库：[yibie/awesome-jev](https://github.com/yibie/awesome-jev)

案例集中反复出现的模式是：从大集合里筛选、给候选打分、按规则路由、检查动作是否安全，以及用置信度决定是否继续。这证明 Jev 更适合作为实时软件中的判断原语，而不是另一个聊天入口。

## 想法如何演化

### 1. 专家匹配

最初设想是：找回 100 个专家后，让 Jev 判断每位专家和需求的匹配度。

这个场景可行，典型做法是：

- 先用结构化硬条件过滤。
- Jev 对剩余候选回答多个 Score/Boolean 问题。
- 分开评估领域相关性、经验适配、可交付性、风险和证据充分度。
- 使用阈值与置信度形成候选集，而不是让模型凭空写一个总分。

它很实用，但 Jev 主要躲在列表排序背后，难以直观看出“动态决策循环”的魅力，因此没有成为当前实验项目。

### 2. 动态报表、DAX 式 DSL 与动态 UI

第二个方向是让用户描述问题，系统选择指标、维度、过滤和视觉组件，几秒内形成一个可保存的动态页面。

关键判断：模型不应该每次生成整页前端代码。更合理的体系是：

- 指标 DSL 定义可计算内容。
- 组件 Registry 定义可以展示的图表、表格、指标卡和过滤器。
- Jev 负责选择指标、组件和布局候选。
- 计算结果与 UI Patch 可以缓存和保存。
- 生成式模型只处理自然语言解释或无法模板化的小部分。

这个方向仍有价值，未来 JevPet 的调试面板、状态卡、回忆卡和选择卡会先验证同一套动态 UI 思路。

### 3. 虚拟互动宠物

最终选择虚拟宠物，是因为它能把 Jev 的特点直接变成可见体验：

- 状态不断变化，可持续产生新的决策上下文。
- 动作有限但组合很多，适合动态能力空间。
- 每一步都可以动画化，决策是否合理一眼可见。
- 可以先完全本地运行，再逐步加入 Jev 和便宜对话模型。
- 同一架构可以不断添加动作、物品、房间、记忆和个性，而不必重写主循环。

它本质上是一个可观察的 Agent Runtime，而不只是一个宠物 App。

## 已确定的产品方向

### 房间是主舞台

用户进入的是宠物正在生活的空间，而不是聊天消息列表。宠物可能在睡觉、看窗外、玩东西或走向用户；对话输入只是房间中的一个入口。

### 宠物有连续状态

情绪、精力、饱腹、亲密度、位置和最近事件会跨会话保存。宠物的反应应能被这些状态解释，不能每次输入都像重置人格。

### 先响应，再思考

点击后立即出现注视、耳朵抖动或短音效。复杂规划可以晚一点返回，再自然接入后续动作。用户不应等待网络后才看到任何反馈。

### 模型不拥有动作执行权

所有动作来自 Action Registry，经过 schema 与参数校验，由 Executor 执行。未知能力、越界参数、超时计划一律拒绝并回退到本地行为。

### 对话是增强层

宠物即使不会自由对话，也应该通过位置、动作、声音、状态和节律形成陪伴感。便宜对话模型以后只负责润色已经确定的意图。

## 视觉方向

![JevPet 房间与宠物概念图](../assets/references/jevpet-room-concept-v1.png)

概念图已经表达出以下可保留方向：

- 移动端纵向构图，房间占据大部分画面。
- 暖色自然光、木质、织物、植物和低饱和绿色。
- 宠物位于可活动空间中，而不是固定头像框。
- 宠物轮廓简单、有明显的叶片耳朵与云朵尾巴，适合形成原创识别度。
- 顶部状态信号、底部输入和常用互动形成清晰层级。
- Play、Feed、Cuddle 体现“动词优先”的互动入口。

概念图不应被逐像素复刻：

- 接近摄影的房间渲染成本过高，需要转成可动画、可分层的风格。
- 顶部和底部控件数量需要在真机上验证，避免遮挡主场景。
- 长期使用时应减少常驻 UI，让宠物行为承担更多信息表达。
- 正式角色还需要正侧背视图、表情表、动作表和比例规范。

## 技术方向

已确定：

- Flutter 作为跨平台应用壳。
- Flame 负责 2D 房间、对象层级、点击与游戏循环。
- SQLite 保存宠物、房间和事件日志。
- 客户端采用本地规则优先、Jev 按需介入的分层 Planner。
- 动态 UI 使用组件目录和受限 DSL。
- Jev 与对话模型密钥只能放在服务端或安全环境中。

待原型验证：

- 宠物主动画使用序列帧 atlas 还是 Rive。
- 房间采用 2D 插画、2.5D 分层还是轻量 3D 预渲染资产。
- 服务端使用什么技术栈，以及是否需要在 MVP 后才建立。

## 最小验证顺序

1. 一个房间和一个宠物占位图。
2. 点击后 100ms 内产生本地即时反应。
3. 本地 Planner 返回类型化动作计划。
4. Executor 顺序完成看向、动画、声音和状态更新。
5. 关闭并重开后恢复状态。
6. 加入 Jev，在同一能力集合上做复杂组合。
7. 加入动态 UI 卡片。
8. 最后再增加自然语言陪伴。

## 想法池

以下内容保留，但不进入当前 MVP：

- 宠物根据房间物品形成偏好和习惯。
- 时间、天气和节日改变房间与自主行为。
- 用户添加受 schema 限制的自定义物品包。
- 关系记忆以相册、便签或房间陈设呈现，而不是纯聊天记录。
- 用行为时间线解释“它为什么这么做”。
- 多宠物之间形成关系与能力组合。
- 将动态报表思路用于开发者调试：查看状态变化、计划命中率、回退率和动作耗时。

## 当前结论

JevPet 要验证的不是“大模型能不能演一个宠物”，而是：

> 当软件提供一套可靠、有限、可组合的能力时，快速类型化决策能否让角色呈现出丰富而连续的生命感。

因此项目第一优先级是动作协议、状态连续性、即时反馈和可回放，而不是先接聊天模型。
